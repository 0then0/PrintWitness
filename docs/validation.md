# Reproducible validation

Use Node.js 24.13 or newer. Validation uses disposable loopback servers and project-local files; it needs no accounts, external APIs or production data.

```sh
npm ci
npm run browsers
npm run check
```

On Linux, use `npm run browsers -- --with-deps` to install required browser system libraries and fonts. Run all commands from the repository root.

## Checks

`npm run check` runs these commands in order:
1. `npm run lint`: Biome formatting, recommended lint rules and import organization; warnings fail.
2. `npm run build`: strict TypeScript checking and a production Vite build.
3. `npm test`: deterministic core and localization regressions.
4. `npm run validate`: actual Chromium exports, PDF.js extraction and raster preview rendering, source capture and transport isolation.
5. `npm run test:ui`: browser interaction with the production server, downloads, offline HTML reports and responsive localization.

To run browser UI checks independently, first run `npm run build` and `npm run validate`. UI checks use the PDFs and manifest generated by validation. The UI test server uses port 4187; other fixture servers use ephemeral loopback ports.

## Multipage acceptance fixture

The original [HTML fixture](../fixtures/validation.html) has 96 table records and 109 expectations. Capture waits for `PRINTWITNESS_READY`. One frozen manifest is used for both variants:
- **Broken:** a missing `PW-042` row, one missing approval repetition, a hidden acceptance section with three expectations, and a changed guide destination. Exactly six findings must be mismatches. A duplicate phrase in the unselected appendix must not hide the loss.
- **Fixed:** every expectation must be found in the text layer. All pages must render. The fixture must remain byte-for-byte unchanged.

Both variants span at least four pages; exact pagination can vary with installed fonts. The checks also exercise local-file capture, invalid and overlapping selectors, bounded readiness timeout, corrupt PDFs and explicit exclusions.

## Regression coverage

Core tests cover independent occurrence counts, section isolation, ambiguous and hidden headings, Unicode normalization, word boundaries, line-end hyphenation, Japanese line wraps, row ordering, repeated table headers, cell partition ambiguity, link annotation association, empty-text pages, exclusions and malformed manifests.

Integration regressions check the complete DOM-to-PDF path for unselected text after a section, HTML `br` elements, whitespace between inline elements, contextual exclusions, Japanese wrapping, changed cell partitions and swapped URL annotations inside a combined PDF text item.

Network checks assert that local scripts, styles and read-only data work while cross-origin HTTP requests, cross-origin redirects, writes, WebSockets, WebRTC and escaping file symlinks are blocked. The WebRTC test checks frame API availability and listens for unexpected ICE/TURN UDP packets. The server test sends a malformed request target and verifies that the process continues serving requests.

UI checks exercise capture, broken and fixed printing, existing PDF upload, evidence selection, page navigation, search, filtering, explicit exclusions, manifest import and real JSON/HTML downloads. Offline HTML must render without HTTP requests. All supported locales are checked at widths of 1500, 1024, 390 and 320 px; source forms and errors are checked at desktop and mobile widths. Theme checks cover explicit light/dark overrides, live system changes, saved preferences, invalid or unavailable storage, unchanged PDF rendering and every locale at desktop/mobile widths. Screenshots are saved in `artifacts/ui/themes/`. Catalog tests enforce key and parameter completeness, diagnostic translation, escaping and unchanged document content.

## Artifacts

Generated files stay in the ignored `artifacts/` directory:
- `validation/`: frozen manifest, broken/fixed PDFs, JSON and standalone HTML reports.
- `regressions/` and `network/`: disposable integration sources.
- `ui/`: downloaded reports and browser screenshots, including locale-specific layouts in `ui/locales/`.

CI retains the validation reports and UI screenshots for seven days; external lab downloads and generated sources are not included in that artifact. Do not upload reports from private documents to public CI or issues. PDF metadata, timestamps and font rasterization can vary by operating system; assertions check semantic behavior rather than byte-identical generated PDFs. Automated layout checks detect overflow and clipped controls but do not replace visual inspection.

## Standalone distributions

`npm run desktop:build` builds, archives and tests the native distribution. The separate Desktop workflow covers macOS arm64/x64, Windows x64 and Ubuntu 24.04 x64. Validation uses the actual portable archive and installation payload with the bundled Node runtime and Chromium, rather than relying on the source checkout's runtime. See the [standalone guide](desktop.md#validation) for isolation, lifecycle and PDF assertions.

## External renderer lab

The optional [WeasyPrint #2469 case study](case-studies/weasyprint-2469.md) includes pinned source revisions, an isolated Docker environment, independent extraction/rendering and upstream regression checks, and existing-PDF comparison against one frozen manifest. It documents a `manual` buggy result and a `found` fixed result, including textless-page uncertainty. It requires network downloads during preparation and is separate from the offline project checks. Generated evidence remains in `artifacts/weasyprint-2469/`; only its license-reviewed allowlist is packaged for sharing.

Lab artifact-integrity tests run with `npm test` without Docker or external downloads. They check valid PDF/report identities, changed PDF bytes, mismatched manifests and rejection of swapped PDFs by both verification and packaging before existing outputs can be overwritten.
